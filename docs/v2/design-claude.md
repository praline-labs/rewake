# Design: the Claude Code adapter

Everything on the Claude Code side goes through one official mod, from Claude Code
2.1.287 on (decision 1). The mod is JavaScript the wrapper writes for one run; the Go
side of the adapter launches the harness, receives the mod's calls at the host's
endpoint, and answers them through the core. The overview is in [design.md](design.md).

This document keeps rewake's decisions about the mod: what it is used for, what the host
does with each call, and what is still to be proved live. It does not describe the mod
API. No work on the mod — planning, code or review — starts without the `mods` skill
loaded ([AGENTS.md](../../AGENTS.md#working-on-the-claude-code-mod)), and a call, event
or field named below is named only to say what rewake does with it; its shape, limits and
version history are the skill's ([where the API facts live](#where-the-api-facts-live)).

## Where the API facts live

A fact about the mod API is not written in this repository: the `mods` skill carries it
and is kept current with every Claude Code release (owner's decision, October 11, 2026).
That covers the events and their fields, the `$` calls and their refusals, limits and
budgets, the static-analysis rules, the reasons a mod does not load, the plugin layout,
testing a mod, and what changed between versions. Before a stage 4 run, compare the
version the skill was taken from with the installed `claude --version`.

What stays here: rewake's decisions, its invariants, and what its own probes observed.
An observation of a given day goes into the research documents with the version it was
made on, as a dated record; it is not a statement of the API. A claim below marked
*to verify* is one the skill does not cover, or one where it disagrees with the design;
the probe named beside it decides, and the decision is not changed until then.

## Loading the mod for one run

The wrapper writes the mod into the run's directory — a plugin manifest named `rewake`,
a hooks file naming one module, the module — and passes `--plugin-dir <dir>` to that
launch only. Nothing in the person's settings changes (L1); the directory goes with the
run (L3) and is one of the adapter's protected directories, so no grant reaches it. The
environment variable that once switched mods on is not set.

The module is generated by the wrapper and kept inside the static-analysis rules of the
skill; a test runs the validator on the generated module (`claude plugin validate`), as
the 1.x plugin host test does (`harness/claude/plugin_control_host_test.go`).

The plugin name gives the tools their prefix, `mcp__rewake__<name>`, which no mod can
avoid (`.scratch/v2-recon/mods-tool-naming.md`). A person's own MCP server named
`rewake` would show the same prefix; whether the two collide is P8 (*to verify*). The
skill also records a refusal when another installed plugin of the same name loads first:
a person's plugin named `rewake` is a cause of not loading, named below.

## When the mod does not load

The skill lists the causes and how each shows (flags, settings keys, managed policy, an
untrusted directory, the remote switch, a worker that crashed). rewake finds out in two
ways:

1. **Before the launch**, from what it can read without editing: the person's own flags
   and the settings files Claude Code reads for the keys the skill names. A known cause
   is named in the refusal or note (L2: where, never what). Whether to also run
   `claude plugin test` from a directory with no mod as a no-session preflight is for
   stage 4 to try; the skill says it prints the state.
2. **At the start**, by the mod's hello: `session.start` is awaited before the first
   prompt, and the mod's first act there is a hello to the endpoint. No hello is not
   proof of failure (C3); the host says what it has not observed — "the rewake mod has
   not reported in; mail runs through the shell" — once, to the person and in the run's
   record.

Until a hello arrives, ToolTransport, TurnBoundary, Telemetry and Control are not live
([design-api.md](design-api.md#two-levels-offered-and-live)). For a role that owes
reports the owner's answer 3 applies ([design.md](design.md#the-owners-answers)): a
known cause refuses the launch; a session running without its mod takes no tasks. A mod
that loaded and is later lost takes its capabilities out of the live set when the host
sees the loss. The loss can be of the whole mod set, not of rewake's mod alone: the
skill says Claude Code unloads every non-built-in mod after repeated worker crashes. P5
includes that case, and the host treats any lost mod the same way.

## The mail tools

At `session.start` the mod registers each tool of the set — name, the plain description
and the input schema, all from `tool` ([design-api.md](design-api.md#tooltransport)) —
before the first prompt. Whether registration outlives `/clear`, which runs no new
`session.start`, is P9 (*to verify*; the skill confirms only that no `session.start`
runs). Whether the tools load deferred, behind a tool search, is P8: the design planned
a `tool.describe` hook with `isDeferred: false`; the skill says `$.tool.register`
accepts `isDeferred: false` itself, which is simpler. P8 tries the registration form
first and then whether the model calls the tools reliably.

**Permissions.** A call the mod answers itself in `tool.call` skips the permission check
and its dialog (the skill), so a launch needs no allowance for the tools (1.x needed
one, `mail-bridge-launch.md` rule 3). But a person's `permissions.deny` on an
`mcp__rewake__` tool would then be routed around, which C7 forbids. So before
answering, the mod asks `$.tool.check({tool, input})`: `deny` returns the person's
refusal to the model as a denial; `allow` and `ask` go on, since rewake's own tools are
what the launch is for. A refusal — the person's deny, or a check that cannot be relied
on — runs no effect and **gives no advice to repeat the operation in the shell**, where
that deny does not reach (C7, `mail-bridge-channel.md` rule 7): it names the refusal or
the check that was unavailable, and the host tells main and the person once. Whether
`$.tool.check` reports a deny rule for a mod-registered tool is P8 (*to verify*; the
skill does not cover it); on a version where it cannot, the mod registers no tools —
ToolTransport is not live and the session is briefed as without it — rather than run
tools under a deny it cannot see. The skill notes that a guard hook fails open unless
the failure is caught; the check's failure path is designed to the same rule, as a
refusal and not as an allowance. A transport fault or a missing read proof under a
check that answered `allow` keeps the ordinary fallback (T6, T11).

### How a tool call runs

Decided: **through the host's endpoint, not by a `rewake` process the mod starts.**

1. `tool.call` for `mcp__rewake__<name>` fires in the mod with the model's arguments and
   the reserved fields `tool` and `tool_use_id`, which no rewrite can change; a call
   from a subagent carries `agentId` and is refused — subagents use the shell.
2. The mod sends the call to the endpoint with `$.http.fetch` over the run's Unix socket:
   the tool, the arguments, `tool_use_id`, `$.session.id()`, and the turn the call
   belongs to. `tool.call` carries no turn id, so the turn is the one whose `turn.start`
   the mod has seen and whose `turn.complete` it has not; a call outside an open turn
   has no proven turn, and its pending mark or read is unproven (T7). That the mod sees
   a main-loop `tool.call` only between its turn's start and complete, and that turn ids
   are never reused, are P3 and P9 (*to verify*); until P9 shows the latter, only an
   operation's first attempt may mark (T7). The skill states the hook's time budget and
   what counts against it; the endpoint call is held to it.
3. The host checks that the request came from the mod (below), makes the binding (T2)
   from those harness-supplied ids and the digest of the arguments, and runs the
   operation in a CLI child of **its own image** under the receipts (T3, T4, T10). The
   answer passes the one encoder and bound (T5).
4. The mod returns the answer's text. A refusal returns as a denial where the skill's
   documented denial answer carries the error flag to the model; the design assumed the
   mod could only return text and so could not mark an error. This is a contradiction
   with the skill: P8 checks live whether the denial answer reaches the model as an
   error, and until then a refusal is plain text as designed (*to verify*).
5. **A read counts only on proof of the final result** (T6): what the model is given
   for that `tool_use_id` after every replacement and truncation, not what the tool
   returned. An event that reports the result is not yet that proof: a post-tool hook
   may replace what the model sees, a person's settings hook can replace a result after
   the mod has seen it, and a large result becomes a preview at a size not yet measured.
   The candidates are `classic.PostToolUse` and `classic.PostToolBatch`, the latter
   fired once per batch before the next model request with each call's response. The
   skill documents the hook order for the pre-tool event only, not for the post-tool
   one, and not whether `classic.PostToolUse` fires for a call the mod answered
   without passing it on. **A candidate is accepted only if P2 shows it carries the
   final result** — after another hook's replacement, after a large result's preview —
   compared with what a stand-in model API actually received (`tools/standin`), never
   with a transcript. Accepted, the host acknowledges the parts when the final result
   equals the recorded answer and arrived before the turn's end (T7, T8). **Without such
   a signal the reading tools refuse before their first effect** and say to read with
   `rewake inbox`; the other tools work.

Why not a child the mod starts: such a child is a process below the harness exactly like
a command the model runs in Bash, with the same environment (*to verify*, P10), so the
host could not tell an acknowledgment from the mod from one the model typed; and after
an npm upgrade the path the mod would run names a new build (T10). Through the endpoint
the answer is computed by the wrapper's own build and the acknowledgment comes from
evidence only the harness emits.

**Telling the mod from a shell command.** Every request to the endpoint is checked on
its own: the peer of its connection, by `SO_PEERCRED`, must be **the harness process
itself** — the pid the wrapper started, alive with its start time before and after the
answer, as the grant authority checks its peer (`docs/grants-authority.md`, steps 1–2).
A descendant of the harness is never accepted, since a command the model runs is one.
No secret, token or session carries authority from one request to the next, so a mod
reload, a respawned hooks worker or a dropped connection changes nothing: each request
proves its origin again. This holds only if `$.http.fetch` connects from the harness's
own process: P4 (*to verify*). The skill does not say which process or thread connects,
and it states that installed mods share one worker thread; the 2.1.280 record says a
worker process of its own for every plugin
([research-claude-control.md](../research-claude-control.md)). The two disagree, and the
live result of P4 settles it. **If it does not hold, there is no fallback**, and more
than the tools goes: every capability that reaches the host through the mod —
ToolTransport, TurnBoundary, Telemetry, Control — is not live on that version, since
its hello, turn events and answers are refused alike. A role that must report then
refuses to launch (answer 3 of [design.md](design.md#the-owners-answers)); the shell
carries mail, not a turn's end. So a negative P4 blocks stage 4's working pair until
another trusted channel of events is designed and reviewed; admitting a helper process
back is not that channel. A secret the host hands the mod is not one: after the first
load a shell command may already run, and on a reload it could read and present a
reissued secret first. The threat is the one 1.x tickets answer — a model's command
imitating the tool; a process of the same user rewriting the mod's files is outside it.

The same holds for the endpoint's other callers in the mod — the hello, turn events,
read evidence, control answers. The stream child of [Control](#control) is a descendant,
so it carries no authority: it only signals that something is waiting, and the mod
fetches the request and posts the answer itself.

## The turn boundary

| Event | The mod does | The host does |
|---|---|---|
| `turn.start` (`turnId`) | remembers `turnId`; tells the host | records the start in the core (replaces the boot-clock files of `obs.turn/`) |
| `classic.Stop` | asks the host whether this end may close | runs the confirmation check ([design-rules.md](design-rules.md#turn-outcomes)); the mod returns `{ block: reason }` when it says go on |
| `classic.StopFailure` | tells the host | marks the turn failed; the report waits for the same turn's `turn.complete`, so one E7 event publishes once |
| `turn.complete` (`turnId`, `reason`, `isAborted`, `answer`) | tells the host and waits for its receipt | the turn end operation (E7), named by run and `turnId` |

Events with `agentId` are a subagent's and are ignored. An interrupted turn gives
`turn.complete` with reason `aborted` and no Stop (records of 2.1.280 in
[research-claude-control.md](../research-claude-control.md)).

The confirmation moves from the settings Stop hook to `classic.Stop`: it fires where the
hook would, without one configured, and may answer `block` with a reason; a repeated
stop is marked. The skill's types allow it; that the chain works live — the order of
`classic.Stop` and `turn.complete`, `StopFailure` followed by `turn.complete`, the block
continuing the turn — is P3 (*to verify*).

## Telemetry

`session.measure` after each turn and on a change of limits, and `$.session.usage()` on
start. The mod forwards both; the adapter folds them into `core/session`. The person's
status line is not wrapped (answer 4): the tap and its parser go.

The design hoped `percent` was measured against the auto-compact threshold, so the 1.x
window parser (`telemetry/window.go`) could go (answer 5). The skill says otherwise:
`percent` is against the model's window, and only the costlier usage call with a
breakdown measures against the compaction window. So the parser goes only if that call
is acceptable; P6 asks that, and the cadence of `session.measure` in practice.

## Control

| Verb | How | Known limit |
|---|---|---|
| compact | `$.session.compact({ instructions })` | the host refuses during a turn (`plugin.js`); the skill says the call itself rejects while a turn runs |
| interrupt | `$.turn.abort({ turnId })` | the running turn's id only |
| clear | `$.command.run` with the clear command, as [conversation-reset.md](../conversation-reset.md) designs it | P7 (*to verify*) |

The earlier text here said no call to clear exists; the skill documents `$.command.run`,
which runs a slash command queued until idle. The design's decision is not changed by
that: P7 asks whether the clear command works live through it and whether it raises
`turn.start` and `turn.complete`; if not, Control offers no clear.

Requests reach the mod by a stream, not by polling (answer 6): the mod starts one child
with `$.process.spawn` at `session.start`, which holds a connection to the endpoint and
prints a line whenever something waits. The line is a hint only — no request, no
content, no authority: the child is a descendant of the harness, which a model's command
can be too ([the mail tools](#how-a-tool-call-runs)). On a hint the mod fetches the
request itself and answers through the endpoint, each request checked on its own. A
lost hint costs time, not a request: the mod also asks at each turn event and on a slow
timer. The request files of `core/control` stay the transport between sessions. The
child is started from the wrapper's own image, `/proc/<wrapper pid>/exe`, so it is the
wrapper's build even after the file at the install path is replaced (T10). The skill
says such a child dies when its module unloads or reloads, and that a reload runs
`session.start` again; so the mod starts the child at every `session.start`. Whether
it lives across turns and `session.end` is P10.

## Wake and delivery

Three candidates (decision 6), decided by P1:

| Candidate | What it is | Known |
|---|---|---|
| `$.prompt.submit` | the mod starts a turn with the notice | waits until idle and starts a turn; no steering mid-turn; the model sees a frame naming the plugin unless sent as the person's (the skill); a repeat of `session.start` does not repeat an earlier submit |
| the 1.x line | a line on the session's inbound socket, at a path rewake fixes with the hidden `--messaging-socket-path` (`harness/claude/claude.go:33`), with the inbound gate's receipts | built and tested in 1.x (`docs/delivery-adapters.md`); steers between tool calls |
| the documented messaging | the same inbound socket as documented: `CLAUDE_CODE_MESSAGING_SOCKET` and `CLAUDE_CODE_MESSAGING_TOKEN`; the mod sees `session.receive` and may consume it | documented, not tried by rewake; whether it differs from the 1.x line beyond the token is part of P1 |

The notice could reach the mod by the same stream as control; the host keeps deciding
what to send and when ([design-api.md](design-api.md#wake)). The fate of the 1.x lane,
`inbox/held.go` and its receipts follows P1 ([revision-core.md](revision-core.md#the-delivery-server-and-heldgo)).

## /clear and resume

`/clear` ends the conversation and continues the process under a new session id, without
a new `session.start`; resume gives its own end reason (the skill; whether a branch is
named is P9). The mod tells the host each change of session id, and the run's
conversation binding moves with it, so a call bound to the old conversation cannot
commit into the new one (T2, T7). The skill names `classic.SessionStart`, which fires
after a clear, a resume and a branch with its source, as the natural carrier of that
telling; the choice between it and the end event is for stage 4.

## What the mod never does

It reads no transcript and no prompt text (`turn.start`'s `text` is not forwarded); it
forwards the end's `answer`, which is the report, as 1.x forwards the Stop hook's last
message. It replaces no status line, sends no settings, and does no heavy work in a
hook: the hooks worker is shared and a mod that stalls it is unloaded.

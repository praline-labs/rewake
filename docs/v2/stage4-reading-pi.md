Inference: pi moves fast (about 19 releases in 5 weeks, several breaking for extension code). An adapter generated for one version needs a minimum-version check and a probe suite, as the Claude mod already has. Pin the version pi is launched with.

## 1. Loading an extension without touching the person's config

Facts:
- `pi -e <path|npm:|git:>` / `--extension` loads an extension "from path, npm, or git; repeatable" (NPM docs/cli.md "Resources"; REF usage.md). `--no-extensions` / `-ne` disables discovered, configured and built-in extensions; "Combine --no-* with explicit flags to load exactly what you need, ignoring settings. Example: `pi --no-extensions -e ./my-extension.ts`" (REF usage.md).
- Extensions are TypeScript loaded by `jiti`, no compile step (REF extensions.md "Writing an Extension"). Directory with `index.ts` or `package.json` with `"pi": {"extensions": [...]}` also works; npm deps resolved from a nearby `node_modules` (REF extensions.md "Available Imports").
- Locations otherwise: `~/.pi/agent/extensions`, `.pi/extensions` (project-local, only after project trust), `settings.json` `extensions`/`packages` (REF extensions.md "Extension Locations").
- CLI `-e` extensions load before project trust is resolved and may handle `project_trust` (REF security.md "Project Trust"). `-a/--approve`, `-na/--no-approve` override trust for one run (NPM docs/cli.md).
- Config dir override: `PI_CODING_AGENT_DIR` (default `~/.pi/agent`), `PI_CODING_AGENT_SESSION_DIR`, `--session-dir` (REF environment-variables.md; NPM cli.md). Extensions can register their own CLI flags `pi.registerFlag()` and read `pi.getFlag()` (REF extensions.md).
- Env passes straight through: extension runs in the pi process, so `process.env.REWAKE_*` is readable (inference from "extensions run with full permissions", REF security.md).
Verdict: loading for one run needs no config edit: `pi -e <generated ext dir> ...`. Inference: whether to add `-ne` is a product decision: without it the person's own extensions (and any that register tools/commands with the same names) load too; with it the person loses their extensions in rewake sessions. A private `PI_CODING_AGENT_DIR` isolates settings but also hides credentials (`auth.json`) and models.json, so it is only usable if rewake copies or points to them. The Claude mod precedent (generated mod loaded per launch) maps directly.

### 2.2 Wake (idle wake, busy steer)
Facts (extension, in-process): `pi.sendMessage(msg, {deliverAs:"steer"|"followUp"|"nextTurn", triggerTurn:true})` and `pi.sendUserMessage(content, {deliverAs, expandPromptTemplates})` (REF extensions.md "pi.sendMessage", "pi.sendUserMessage"). `triggerTurn:true` starts an LLM turn when idle. Custom messages enter LLM context (`customType`, `content`, `display`, `details`); `display:true` renders them in the transcript, `registerMessageRenderer` styles them.
- Steer semantics: "Queues the message while streaming. Delivered after the current assistant turn finishes executing its tool calls, before the next LLM call." `followUp`: only "when agent has no more tool calls" (REF extensions.md; REF rpc.md steer; NPM rpc-commands.md). Steering mode `one-at-a-time` by default (`set_steering_mode`). CHANGELOG (REF-era line ~3145): "steering messages wait until the current assistant message's tool-call batch fully finishes instead of skipping pending tool calls". The older "queued message interrupts the tool batch" (CHANGELOG early 0.x, line ~5539) was reversed; current docs are the authority.
- Idle: `ctx.isIdle()` false during run, retry, compaction retry, queued continuation (REF extensions.md); `agent_settled` = nothing automatic left; `ui_prompt_start/end` events say pi is blocked on a dialog (REF extensions.md).
- Mid-run external wake needs an event source inside the extension: Node access is full (`node:net`, `node:fs`, `fetch`, `child_process`) (REF extensions.md "Available Imports"; example `file-trigger.ts` uses `pi.sendMessage(..., {triggerTurn:true})` from a file watcher, REF examples). Caveat: "Do not start background resources from the factory; start in `session_start`, close in an idempotent `session_shutdown`" (REF extensions.md).
- RPC mode: `prompt` (with `streamingBehavior` steer/followUp while streaming; otherwise error), `steer`, `follow_up`, `clear_queue`, `queue_update` event; responses carry `disposition` (NPM rpc-commands.md).
Inference: a rewake notice line maps onto `sendMessage({customType:"rewake-notice", content:<line>, display:true}, {deliverAs:"steer", triggerTurn:true})`. The delivery boundary is the end of the current assistant message's tool batch, not the middle of a tool call. A long `bash` call holds the notice until it returns; there is no built-in "deliver now". With a custom tool or hook the extension can only `ctx.abort()` (hard, loses the tool) to force it. Compared with Claude Code's immediate "● …" line this is later but safe. The held notice is reportable: `ctx.hasPendingMessages()`, RPC `queue_update`.
- 1.2.0 hazard: during `before_agent_start` the session is busy; `sendUserMessage` without `deliverAs` throws. The wake path must always pass `deliverAs` unless it checked `ctx.isIdle()` immediately before (race).
Verdict: native in extension (wake idle + steer busy). Via RPC too (`steer`/`follow_up`/`prompt`), but only for a headless worker.

### 2.3 ToolTransport (mail tools offered to the model)
Facts: `pi.registerTool({name,label,description,promptSnippet,promptGuidelines,parameters:TypeBox, execute(toolCallId, params, signal, onUpdate, ctx), ...})`, callable immediately even after startup; `ctx` gives `sessionManager`, `cwd`, `signal`, etc. Errors are signalled by throwing (sets `isError`); returning does not (REF extensions.md "Custom Tools"). 1.x adds `exposure`, `namespace`, `outputSchema`/`structuredContent`, `annotations` (NPM extensions.md "Tools", "Tool exposure"; CHANGELOG 0.99.0). MCP servers can also be registered per session with `pi.registerMcpServer(name, {command,args,env,url,...})`; tool names become `mcp__<server>__<tool>` with `-` replaced by `_` (NPM extensions.md "MCP servers"; CHANGELOG 0.99.2). `--tools` allowlist keeps extension tools; if `--tools` is used rewake's tool names must be in it, and `mcp__*` tools are dropped only if an entry starts with `mcp__` (NPM cli.md).
- Binding ids a tool call can supply itself: `toolCallId` (argument of `execute`), `ctx.sessionManager.getSessionId()` (REF extensions.md `before_provider_headers` example uses it), `ctx.sessionManager.getSessionFile()`; turn index via `turn_start` event `turnIndex` tracked by the extension. All come from inside the pi process. Parallel tool calls are the default ("In the default parallel tool execution mode, sibling tool calls ... executed concurrently", REF extensions.md `tool_call`); `pi.registerTool` has a sequential option for shared mutable state (NPM extensions.md "Use sequential execution when tools share mutable in-memory state"; exact flag name = probe).
- Subagent identity: pi core has no sub-agents ("intentionally does not include ... sub-agents", REF usage.md; README 1.2.0). The `examples/extensions/subagent` extension spawns separate `pi` processes (REF examples/extensions/subagent/index.ts:346 `spawn`), which are different processes and would not load the rewake extension unless told to; but they inherit env (`REWAKE_*`). Inference: a person's own sub-agent extension would carry the parent's `REWAKE_SESSION` into child pi processes; child pi processes without `-e` would simply have no tools, but a tool-using shell in them could still call `rewake` by CLI with the parent's env. Same class of risk as T-rules for subagents on Claude; the extension must identify its own process (pid or nonce), not rely on env.
- Execution path from tool to host: extension is Node; it can open the host endpoint (unix socket) directly in `execute`; no MCP transport needed. Alternative: `pi.exec("rewake", [...])`.
Verdict: native in extension, no wrapper needed. Descriptors -> TypeBox schema is a mechanical render. The `tool` / `consent` reserved-property problem of Claude Code does not exist here; pi's reserved parts = none seen (inference: probe).

### 2.4 TurnBoundary
Facts: events `agent_start`, `agent_end {messages, willRetry}`, `agent_settled {aborted}` (aborted since 1.1.0), `turn_start {turnIndex, timestamp}`, `turn_end {turnIndex, message, toolResults}`, `message_start/update/end`, `tool_execution_*` (REF extensions.md "Agent Events"; NPM docs/json.md, CHANGELOG 1.1.0). Same stream over RPC/JSON mode (NPM json.md "Agent and turn events"; rpc.md "Run lifecycle").
- "agent_end marks the end of one low-level agent run, but retries, overflow recovery, compaction, steering, or follow-up work can still follow. Wait for agent_settled" (NPM rpc.md "Run lifecycle"). So rewake's turn end should be `agent_settled`, not `agent_end`.
- "Confirms an end before it closes": `agent_before_settle` is "the final actionable boundary: it can append entries and request one continuation" (NPM extensions.md "Respect the runtime lifecycle"); `turn_end` is also actionable since 0.87.0. Handlers can persist entries and return `continue:true`. That is a native hook for "verify the report was sent before the turn ends" and even to force one more request ("you still owe a report"). Guard against loops (docs warn).
- The answer of the turn: last assistant message in `agent_end.messages` / `message_end` (role assistant) with `stopReason`: "stop|length|toolUse|error|aborted" (REF session-format.md "AssistantMessage"). RPC `get_last_assistant_text` exists.
- Subagent turns excluded: not applicable (no built-in sub-agents); nested `ctx.executeTool()` calls are not turns (they carry `parentToolCallId`).
- Stop reasons: user abort (Esc) shows as `aborted`; `agent_settled.aborted` exposes it (1.1.0). That maps to rewake's "stopped" kind.
Verdict: native in extension and via RPC. Strong match, arguably better than Claude's (explicit settled + actionable pre-settle boundary).

### 2.5 Telemetry (context, limits, cost, model, effort)
Facts: `ctx.getContextUsage()` -> `{tokens, ...}` for the active model, estimated from the last assistant usage (REF extensions.md). RPC `get_session_stats` -> `tokens{input,output,cacheRead,cacheWrite,total}`, `cost`, `contextUsage{tokens,contextWindow,percent}`; "`contextUsage.tokens`/`percent` are null immediately after compaction until a fresh response" (REF rpc.md "get_session_stats"). `get_state` -> model object (id, provider, contextWindow, maxTokens, cost per Mtok), `thinkingLevel`, `isStreaming`, `isCompacting`, `sessionFile`, `sessionId`, `pendingMessageCount`, `autoCompactionEnabled` (REF rpc.md "get_state"). Per-message `usage` incl. `cost.total`, `provider`, `model`, `providerThinkingLevel` on AssistantMessage (REF session-format.md). `model_select` / `thinking_level_select` events; `ctx.model`, `ctx.thinkingLevel`, `pi.getThinkingLevel()`: "off|minimal|low|medium|high|xhigh|max", clamped to model capability (REF extensions.md). Shell commands run by the model get `PI_SESSION_ID`, `PI_SESSION_FILE`, `PI_PROVIDER`, `PI_MODEL`, `PI_REASONING_LEVEL` (REF environment-variables.md).
- Virtual models: selected model and effort differ from the dispatched physical model; the assistant message names the physical model; `ctx.model` = the virtual one; "Context usage uses the limits of the physical model that produced the latest response" (NPM virtual-models.md). Telemetry should read both.
- Limits (rate/usage windows): I found no provider quota or rate-limit window reporting in pi docs or changelog (grep of NPM docs + CHANGELOG for rate limit/quota/remaining returns only retry handling: NPM settings.md "retry.provider.maxRetries ... quota and usage-limit errors"; REF CHANGELOG 0.80.x on 429 retry). Inference: "limits" would be unknown in `list` for pi; cost is available and context % is available.
- Models without known context window: `contextUsage` omitted when no context window (REF rpc.md).
Verdict: native in extension and RPC for context/cost/model/effort; limits missing.

### 2.6 Control: compact / interrupt / clear
Facts: `ctx.compact({customInstructions,onComplete,onError})` available in any ExtensionContext (non-blocking) (REF extensions.md "ctx.compact()"); RPC `compact` (+ `customInstructions`), `set_auto_compaction`; events `session_before_compact` (can cancel/customize), `session_compact`, `session_compact_failed`, RPC `compaction_start/end` (REF extensions.md/rpc.md). Compaction uses an LLM call with the session model (REF compaction.md "How It Works"); a message submitted during compaction is queued and delivered after, but a direct `prompt` throws "Cannot submit a prompt while compaction is in progress" (REF src/core/agent-session.ts:1190-1198 -> extension commands still run).
- Interrupt: `ctx.abort()` (ExtensionContext) and RPC `abort` ("waits for the session to become idle before responding") (REF extensions.md "ctx.isIdle()/ctx.abort()"; rpc.md). After abort queued messages continue unless `clear_queue` first (REF rpc.md "clear_queue"). `agent_settled.aborted=true` follows.
- Clear: `ctx.newSession()`, `ctx.fork()`, `ctx.switchSession()` are only on `ExtensionCommandContext` ("These are only available in commands because they can deadlock if called from event handlers", REF extensions.md). RPC `new_session` (optional `parentSession`) exists; interactive `/new`. Session replacement tears down the old extension runtime and creates a new one; old `pi`/`ctx` objects are stale and throw (REF extensions.md "Session replacement lifecycle and footguns").
- Fact from source: `pi.sendUserMessage("/cmd", {expandPromptTemplates:true})` dispatches an extension command, and `prompt()` runs extension commands "immediately, even during streaming" before queueing logic (REF src/core/agent-session.ts:1170-1195, 1569). Inference: a socket event in the extension can run `/rewake-clear` (registered with `pi.registerCommand`) through that path and get a command context with `newSession`. Not proven; probe it (also while idle and while streaming).
Verdict: compact native; interrupt native; clear = native in command context (reachable from an extension via a self-sent command, to confirm) or RPC `new_session` for a headless worker. After `/new` the extension instance is rebuilt and receives `session_start {reason:"new", previousSessionFile}`; its bound state (socket, binding, nonce) must be restored from module scope or re-registered.

### 2.7 Permissions (write grants per task)
Facts: "Pi does not include a built-in sandbox. ... Extensions ... run with the same permissions" (REF security.md "No Built-in Sandbox"). 0.85.1 and 1.2.0 both: "intentionally does not include ... permission popups". Project trust only guards loading of `.pi` resources. Primitives: `tool_call` event can block (`{block:true,reason}`) and mutate `event.input` before execution, for `write`, `edit`, `bash`, custom tools alike; handlers errors fail closed (REF extensions.md "tool_call"; examples `protected-paths.ts`, `permission-gate.ts`, `confirm-destructive.ts`). `user_bash` fails closed (0.86.0). Built-in tools can be replaced/overridden by registering the same name (REF extensions.md "Overriding Built-in Tools"; `sandbox/index.ts` wraps bash with bubblewrap via `@anthropic-ai/sandbox-runtime`: filesystem allowWrite/denyWrite and network allow list). Tool `annotations` (readOnlyHint, destructiveHint) are available to a permission gate (NPM extensions.md "Tool exposure"). Containers: Gondolin micro-VM, Docker, OpenShell (REF containerization.md).
Inference: write grants enforced at the tool level: path check in `tool_call` for `write`/`edit` is easy and reliable for the built-in file tools. For `bash` (and anything the model runs through a shell, a language runtime, git) a path check is impossible; real enforcement needs OS-level confinement (bwrap/landlock via the `sandbox` example, a container, or Gondolin). That is stronger than Claude Code's grants only if rewake itself runs pi under bwrap with the granted paths writable; otherwise grants are advisory. Protected dirs (`ProtectedDirs`): `.pi/`, `~/.pi/agent` (settings, auth.json, extensions), and the extension's own socket dir. A model could rewrite `~/.pi/agent/settings.json` or the extension file; same caution as `.claude`.
Verdict: partial. Native hook (`tool_call` block) for built-in file tools; shell writes need an OS sandbox (wrapper). Do not claim grants are enforced without bwrap.

### 2.8 PersonUI
Facts: interactive TUI has `ctx.ui.setStatus(key,text)` footer entries, `setWidget(key, lines|component, {placement})` above/below editor, `setFooter`, `setHeader`, `setTitle`, `notify`, dialogs (`select/confirm/input/editor`), `custom()` full component or overlay with focus, anchors (REF extensions.md "Custom UI", tui.md). RPC mode forwards dialogs, `notify`, `setStatus`, `setWidget` (string lines), `setTitle`, `set_editor_text`; `custom()`, `setFooter`, `setHeader`, `setEditorComponent` are no-ops/undefined there (NPM rpc-extension-ui.md; REF rpc.md "Extension UI Protocol"). `ctx.hasUI`, `ctx.mode` = tui|rpc|json|print. A message renderer can show mail in the transcript (`registerMessageRenderer`, `registerEntryRenderer`). TUI emits OSC 7501 status for terminals (1.1.0).
- "A tab hosting a worker in a pseudo-terminal rewake owns": two readings.
  (a) rewake owns the PTY and runs interactive `pi` (TUI) inside it; the tab is a terminal emulator view of that PTY; pi needs no cooperation. Native; works with `--tui-mode regular|fullscreen`. Nothing in pi prevents it (it checks `process.stdout.isTTY`, REF src/modes/interactive/interactive-mode.ts:272; non-TTY -> print mode per NPM cli-integration.md).
  (b) draw a PTY inside a pi UI component (a pi session hosting another program). pi gives `ctx.ui.custom()` overlay components that render `string[]` lines and get raw key input (`handleInput`), `doom-overlay` is a precedent for a continuously rendering component with raw key forwarding (REF examples/extensions/doom-overlay). Spawning a child: `node:child_process` works, but a PTY needs `node-pty` (native add-on, not in pi's dependency list), or a helper binary (rewake itself). A terminal emulator layer (parse ANSI into a cell grid) is needed as pi expects lines that fit the width and warns "Do not create a second terminal renderer inside an extension" (NPM tui.md). Inference: feasible but heavy; not the natural direction. (a) is the natural one and matches the rewake-owned-PTY idea; for (a) the extension reports state to rewake and rewake draws it.
Verdict: PersonUI notice/status native (`setStatus`, `setWidget`, `notify`, message renderer); the PTY tab = rewake's own work, outside pi (wrapper).

## 3. Headless worker via RPC (`pi --mode rpc`)
Facts: JSONL over stdin/stdout, LF-only framing (Node `readline` is not compliant), `id` correlation, events streamed, `RpcClient` class exported (`./rpc-entry`), extensions load in RPC mode (dialogs via `extension_ui_request/response` sub-protocol; `ctx.hasUI` true, `ctx.mode "rpc"`) (NPM rpc.md, rpc-extension-ui.md, package.json exports). Command set: prompt, steer, follow_up, abort, clear_queue, new_session, get_state, get_messages, set_model, cycle_model, get_available_models, set/cycle thinking level, set_steering_mode, set_follow_up_mode, compact, set_auto_compaction, set_auto_retry, abort_retry, bash, abort_bash, get_session_stats, export_html, switch_session, fork, clone, get_fork_messages, get_entries, get_tree, get_last_assistant_text, set_session_name, get_commands (NPM rpc-commands.md). Shutdown by closing stdin. "RPC mode rejects `@file` prompt arguments" (NPM rpc.md). Run lifecycle: wait for `agent_settled`; `data.disposition == "handled"` means no run started (NPM rpc.md).
Inference: for background workers (no person attached) RPC alone gives wake, steer, interrupt, compact, clear (new_session), telemetry, model/effort control, with no extension at all except for ToolTransport (still an `-e` extension, or MCP). The host then owns stdin/stdout of pi, so a person cannot type into it; a person-visible worker needs the TUI. So there are two process shapes: RPC (rewake is the client) and TUI (extension is the client; rewake reads state through a socket the extension serves). Two code paths to build and test; the extension path covers both if the extension does the work and RPC is only the carrier for headless. RPC `new_session` and extension command context are different paths for clear.
Also available: SDK (`createAgentSession`, `AgentSessionRuntime`) for a Node host embedding pi in-process; rewake is Go, so it would need a Node sidecar (not recommended; RPC does the same).

## 4. Sessions: file format and ids across /new, fork, resume
Facts: JSONL at `~/.pi/agent/sessions/--<cwd with / replaced by ->--/<timestamp>_<session-id>.jsonl`; id is a UUID by default or caller-chosen (`--session-id`, SDK) (REF session-format.md "File Location"). Header line `{"type":"session","version":3,"id","timestamp","cwd","parentSession?"}`; entries have `id`/`parentId` (tree). `/tree` moves the leaf inside one file (same session id); `/fork`/`/clone` write a new file with a new id and `parentSession` in header; `/new` creates a new file; `/resume` / `--session` opens an existing one (REF sessions.md; session-format.md; NPM sessions.md "Choose how to branch"). Extension events: `session_start {reason:"startup"|"new"|"resume"|"fork", previousSessionFile?}`, `session_before_switch`, `session_before_fork` (both can cancel), `session_shutdown`, `session_tree`, `session_info_changed` (REF extensions.md "Lifecycle Overview"). `new_session` and `switch_session` also appear as RPC commands and return `{cancelled}`.
- File is created when the first user message is sent (0.99.0 fix; NPM CHANGELOG 0.99.0), so a freshly started session has no file until the first prompt. `--no-session` gives no id persisted (env `PI_SESSION_FILE` unset).
- Compaction does not delete entries; adds a `compaction` entry with `firstKeptEntryId` (REF compaction.md).
Inference: rewake's "conversation" binding = `sessionId` (stable across `/tree`, compaction, reload; changes on `/new`, `/fork`, `/clone`, `/resume` into another file). A pi user doing `/new` inside a rewake session replaces the conversation id exactly as `/clear` does on Claude; the extension sees `session_start reason:"new"` and can report the replacement to the host; cancel is possible with `session_before_switch` returning cancel (Rewake could refuse a person's `/new` when a report is owed; design decision, not a limit). `--session-id <rewake-chosen id>` lets rewake name the session up front, which gives a binding known before the first turn (no Claude equivalent that I know of); check that `PI_SESSION_ID` equals it.

## 5. Identity of the process
Facts: the extension runs in the pi process; `process.pid`, env, `ctx.sessionManager.getSessionId()/getSessionFile()` are available to it (REF extensions.md). Bash commands run by the model receive `PI_CODING_AGENT=true`, `PI_SESSION_ID`, `PI_SESSION_FILE`, `PI_PROVIDER`, `PI_MODEL`, `PI_REASONING_LEVEL` resolved at command start (REF environment-variables.md). The wrapper can set `REWAKE_*` env on spawn; extension inherits it.
Inference: strong identity chain possible: wrapper spawns `pi` (pid known), passes a nonce via env, extension (same pid) presents nonce + `process.pid` + sessionId to the host; the model's shell commands carry `PI_SESSION_ID` which the CLI can compare with the registered binding (cheap cross-check for `rewake inbox` run from the shell; a sub-process pi started by the model via bash would carry its own different `PI_SESSION_ID`, so can be told apart; env nonce alone is copyable by any child). Open: when pi is started by a node launcher (`dist/bundle/cli.js` via `#!/usr/bin/env node`) the pid wrapper spawned is the node process = pi; verify no re-exec/detach.

## 6. "Any model": providers and custom/local
Facts: multi-provider layer `@earendil-works/pi-ai`; built-in providers via `/login` (subscriptions: Anthropic, OpenAI/ChatGPT, GitHub Copilot, Google, etc.), API keys in env, `--api-key`; Bedrock, Vertex, Azure (renamed `azure` in 1.0.3), Cloudflare, OpenRouter, Radius, Meta Muse, xAI, Mistral listed in providers.md/CHANGELOG. Custom endpoints: `models.json` with `api: "openai-completions" | "openai-responses" | "anthropic-messages" | google ...`, `baseUrl`, `apiKey` (literal, `$ENV`, or `!command`), per-model `reasoning`, `input`, `contextWindow`, `maxTokens`, `cost`, `compat.*` knobs; "For Ollama, LM Studio, vLLM, SGLang, and other compatible servers" (NPM models.md "Configure a compatible endpoint"). llama.cpp router built in (`/llama`). Extension `pi.registerProvider()` for custom protocols and dynamic model lists (REF extensions.md "Async factory functions"). Model catalog bundled and refreshed from pi.dev; offline cached (`PI_OFFLINE`).
Inference: this is real. Compatibility depth varies: tool calling quality, thinking replay, and `compat` flags are per-provider; the "any model" claim holds for transport, not for equal agent quality. Telemetry fields (context window, cost) come from the catalog or models.json; for a custom model with no declared `contextWindow` context % may be missing. The rewake side must not name providers (provider-agnostic rule) and should treat model id as an opaque string plus `provider`.

## 8. Biggest risks
1. Churn: breaking changes in extension APIs in five weeks (0.86 -> 1.2); 1.2.0 docs no longer carry the API text. Mitigation: pin version, probe suite, minimum version in adapter.
2. Steer is delayed until the assistant message's tool batch ends; a long tool call delays the notice and any "busy steer" promise. Interrupt is the only escape and is destructive.
3. No permissions: grants for shell writes are not enforceable without OS sandboxing; this is a documented design stance, not a bug to wait for.
4. Extension runtime is torn down and rebuilt on `/new`, switch, fork, reload; stale `pi`/`ctx` objects throw. A person's `/new` or `/reload` changes the binding and loses in-memory state unless held at module scope and re-registered on `session_start`.
5. Two process shapes (TUI + extension vs RPC) = two paths to keep equal. RPC owns stdin/stdout so a person cannot attach.
6. The person's config leaks in: other extensions, settings, `AGENTS.md`/`CLAUDE.md` context files (loaded regardless of trust), tools; `-ne` costs the person their extensions. User/global extensions can themselves register tools named like rewake's.
7. `limits` telemetry absent; `contextUsage` null right after compaction; custom models may lack context window.
8. Subagent-like extensions in the person's setup spawn child `pi` processes inheriting `REWAKE_*` env.
9. Fullscreen TUI is the default since 1.0.0 (changes anything that scripts the TUI; irrelevant if rewake only uses the extension + a PTY it does not parse).
10. Supply chain: extension is arbitrary code in the process; npm install in `-e npm:` or extension deps runs outside rewake's control; prefer a local generated file with no dependencies (rewake's Node code uses only `node:` built-ins and `typebox` which pi supplies).

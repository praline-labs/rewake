# Stage 4 of 2.0: the mod loaded per run and spaces in the adapter API

Step S4-5 of the first working space
([the steps](../v2/stage4-space-steps.md#the-build-steps)), built October 13, 2026 on branch
`s4-5` from `v2` at `f045ab6`, in two parts: A, the mod and its endpoint, reviewed on the Codex
side; B, the spaces capability and the conversation's name in the adapter API. The five checks
ran green on each part's last commit. It lands on `v2` once the review of A's fix and of B
accepts it.

## What it built

- **Part A, the mod for one run** (`e00d55d`). The mod's files are embedded in the binary from
  `internal/adapter/claude/mod/` and written into the run's directory before the harness
  starts; the launch adds `--plugin-dir` and names the run's mod socket in the harness's
  environment. At `session.start` the mod says hello with its load's id, the session's id and
  the harness's version. `internal/adapter/claude/modhost` answers on the socket, checking every
  request by its peer: only the harness process the wrapper started, alive with its start time,
  is served, before the answer as well as on arrival (SP4); the host names that process to the
  service through `HarnessWatcher`. Three tests hold the files: the embedded copy is the source,
  the written mod passes `claude plugin validate --strict`, and the mod's own tests pass in
  `claude plugin test` ([loading the mod](../v2/design-claude.md#loading-the-mod-for-one-run)).
- **Part B, spaces and the conversation's name** (`b964db5`). Spaces are a capability like the
  others: offered by the adapter, proven live by a run, never planned, and refused by the level
  that is missing — the role (main alone opens a space), the harness's offer, the run's live
  set ([spaces](../v2/design-api.md#spaces)). On Claude Code a main run's admitted hello makes
  them live, and its answer tells the mod it hosts spaces. Every adapter's offer says whether a
  launch can name its conversation, a flag or the reason there is none; Claude Code answers
  `--session-id <uuid>`, the fixture answers that it takes none
  ([conversation names](../v2/design-api.md#conversation-names)). Catalog tests hold both, so
  an adapter cannot be half-described for them.

## What the review found and how it was fixed

- **A: the endpoint's handlers outlived its close.** `Server.Close` waited only for the accept
  loop, so a hello's record could be written after the close returned, after the run's
  directory went and after the room's lease was released; main confirmed it with the
  reviewer's probe, a write stalled in a FIFO. Fixed in `bf6d0e3`: the handlers count among the
  run's workers through `WorkerCounter`, so the lease and the directory outlast the last write;
  the close is bounded, and a handler that has not begun its record writes nothing once the
  server is closed; a hello's binding and its record are one step under one lock. The probe is
  kept as a regression, beside a test of hellos at once.

## Live

On Claude Code 2.1.296, by main: the probe's kit answered P4 positive — every request the mod
made came from the harness process itself, through a reload and the keeper's hold, and a
model's shell child was refused; rewake's own mod then said hello on a launched run in `-p`
mode, its hello admitted and recorded, a model's shell child answered 403
([the record](../research-claude-mod.md#p4-the-peer-of-the-mods-requests)).

## What stays open

- P4 on a hooks worker respawned after a crash, and a shell child started before a reload.
- A lost mod withdraws its spaces when the host sees the loss, the signal S4-6 builds with the
  turn boundary; until then the run's end is the only loss observed.
- `rewake space open` and the host's space seam are S4-7's; the fixture gets spaces and a
  conversation flag there, through that seam and never through another adapter's mod.
- The hello names no list of what the mod serves; a launch through `--command` names the
  wrapper script as the harness, so such a run's mod is never admitted.

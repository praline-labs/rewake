# Stage 4 of 2.0: P15b, a real pseudo-terminal in the keeper's row

The second half of P15 in stage 4's probe ([design-claude.md](../v2/design-claude.md#the-stage-4-probe)),
October 13, 2026, on Claude Code 2.1.296 with the `mods` skill of the same version. Main ran
it live from the kit in the ignored `.scratch/`; the write session extended the kit — a
helper owning a real pseudo-terminal with a VT emulator, the key surface turning keys and the
prefix into terminal bytes — ran only its dry mode and the validator, and recorded the results
on branch `s4-space-design` from `v2` at `32f3ab3`. Documents only: no code changed. The record
is [research-claude-mod.md](../research-claude-mod.md#p15b-a-real-pseudo-terminal-in-the-keepers-row).

## What ran and what it answered

- **A shell, vi and less** (runs `rRg9nU`, `R9hqiI`, `lFafj9`). Every key typed in the key
  surface, and the prefix's Ctrl+C, Escape, Ctrl+X and Alt+a, reached the pseudo-terminal as
  the bytes a terminal sends; key to echo took 31 ms at the median over the whole path. Escape
  through the prefix worked in vi.
- **A nested Claude Code** (runs `A3TDXM`, then `vI91jc`). It started in the keeper's worktree
  with no trust question, answered a prompt typed through the key surface, was repainted live
  in the keeper's view, and ended on the prefix's Ctrl+C twice. The first run stalled on a kit
  bug — the keeper's second call took over the repaint — and its two Ctrl+C were 1.95 s apart;
  the kit was fixed and the second run went end to end.
- **The keeper's second call** came about 30 s after the first in every run that held it,
  under an agent id `$.agent.list()` never listed; answered "already held", it did no harm.

A correction to the first runs' record: in run `woP6c8` the keeper's first call ended with
"lost its server" because the kit asked each poll to wait longer than `$.http.fetch` allows,
not because of Claude Code.
